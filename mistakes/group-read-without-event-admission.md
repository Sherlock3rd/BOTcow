# 群历史可读但群指令未响应

## 2026-11-03 现象与根因

- 用户将机器人加入群并 @ 发出任务。接收事件已写入 inbox，开通 im:message.group_msg 后历史读取成功，但没有 OnIt 或回复。
- 本地 allowed_chat_types 仍只有 p2p；监听器的表情/唤醒入口及 queue pending 都过滤了 group。读取权限生效不能代替自动处理验收。

## 修复与范围

- 抽出 bridge-eligibility.mjs，共享监听和队列的判定。
- 只放行配置中明确的群、既有用户白名单、真实 mentions 中的 bot open_id；普通聊天、其他群或其他用户均不触发。
- 对两条已记录的群指令补 OnIt 并回读；原指令下回复真实状态。业务未完成，不添加 DONE、不 mark。
- 新监听器加载修复；串行 worker 恢复处理原群任务。

## 切换失误与防呆

- 本次误以为 stop-bridge 的源码只停止 consumer 就能保留 worker，但 Windows 实测监听器退出后，原 worker 和 Codex 子进程也消失，且状态文件仍写 running。队列未丢失，已用持锁的原唤醒脚本恢复。
- 不得仅凭 shutdown 源码推断子进程存活；后续切换必须等待 worker 安全结束，再停止监听器，并核对真实 PID、命令行及 pending。不要重复此次活跃 worker 期间的切换。
- 验收区分历史读取、消息准入、即时表情、模型运行、业务完成及群内结果回复；未完成的环节明确标注。

## 2026-11-13 授权范围更新与公开通道防呆

- 用户已授权既有白名单群内其他真人成员真实@时响应。上述“其他用户均不触发”是旧范围；现在访客仅进入独立、无工具、无私人上下文的公开短答通道，原发送者白名单仍决定业务执行权限。
- 准入扩大不等于记忆或业务授权扩大：memoryScope 和业务执行入口必须另行核对原发送者白名单，不能仅凭 eligibleMessage 为真就授予权限。
- 公开通道不读取历史、引用和内部知识；模型错误、伪造任务标记、旧fallback均不得转入业务执行器。已补对应回归，原白名单请求在访客积压时优先。
- 激活先确认无处理锁及pending，停止旧监听和旧chat worker，再写group_public配置并启动；不能让旧进程先读取扩大后的权限。保留enabled_at，避免翻出旧访客消息。

## 2026-11-14 管理员邀请即授权

用户撤销了每新增群都要回Codex确认的交互：本人拉机器人进群即授权接入。通过真实 im.chat.member.bot.added_v1 的 app_id 和 operator_id.open_id 核对管理员，动态准入，不读取消息自称作为授权。移出事件撤销；启用前和邀请前历史不回放。要同时核对后台事件订阅、成员consumer状态、动态投影和真实回复，不能只看到普通消息ready就宣称自动入群生效。原始成员事件header含token，只持久化最小投影。
