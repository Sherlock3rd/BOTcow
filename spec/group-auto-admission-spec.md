# 管理员邀请入群自动接入

版本：v1.0，2026-11-14。用户已明确授权：本人把机器人拉进群即授权该群响应，无需再到 Codex 确认。

## 事件与准入

- 使用 bot 身份订阅 `im.chat.member.bot.added_v1`、`im.chat.member.bot.deleted_v1`；消息仍订阅 `im.message.receive_v1`。
- 本机 CLI `event schema` 确认：前两者是原生 V2 envelope，字段为 `header.app_id/event_id/event_type/create_time` 与 `event.chat_id/operator_id.open_id`；不能沿用消息事件的扁平字段路径。
- 只接受当前应用、启用时间之后的真实入群事件；邀请者必须在 `allowed_sender_ids` 中。其他人邀请、普通消息中的自称、引用或转发不授予群权限。
- 入群时写入 `runtime/group-admissions.json` 的最小状态；不保存原始 envelope，其 header 含校验 token。
- 群内仍只响应真实 @；管理员保留已有业务能力，其他成员保持无工具短答和原预算，不获得记忆、内部知识或个人身份权限。
- 仅处理消息创建时间不早于该次邀请的消息。旧事件、重复投递、乱序事件不会覆盖较新状态；同时间移出优先，重邀须晚于移出时间。
- 移出事件撤销群准入，包括遮蔽静态白名单；再次由管理员邀请才恢复。状态损坏或应用身份不符时拒绝群准入，不猜测为空状态。

## 加载与失败

动态状态由同一监听器原子写入，监听、队列和工作进程使用共同准入函数实时读取。因此后续自动入群不需要重启或等待其他业务结束。静态配置、开关和模型变更仍遵循原安全重启流程；多个业务任务并行未实现。

三个事件分别使用 consumer，某个订阅失败不停止原消息监听。缺权限、后台未订阅等确定性失败写入独立 `*.status.json` 的 blocked 状态，不无限重试；修复后台后安全重启监听器以重新订阅。ready 仅证明消费连接就绪，仍需真实新邀请和群回复验收。

配置：`auto_group_admission.enabled`、`app_id`、`enabled_at`。新部署先核对本应用身份与事件订阅，填写启用时间，再开通；禁止把其他部署的动态准入文件复制过来。

## 验收

回归须覆盖管理员入群、陌生人/错误应用拒绝、旧事件拒绝、幂等、乱序、移出、重新邀请、热读取、群访客记忆隔离和原始 token 不落日志。监听集成测试使用独立临时目录及模拟 CLI，不向飞书发消息。上线分别记录测试、进程就绪、两个后台订阅状态、真实邀请及回复回读，不能合并成笼统“全部通过”。
